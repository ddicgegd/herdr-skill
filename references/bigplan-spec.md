# BigPlan Specification

A BigPlan is the durable, complete business and engineering plan for one initiative. It is the source of truth for intent, rules, design, work structure, and acceptance; it is not a roster or wave checklist.

## Folder structure

```text
docs/plan-herdr/<initiative-slug>/
├── bigplan.md
├── context-and-decisions.md
├── business-rules.md
├── solution-design.md
├── work-map.yaml
├── tasks/
│   ├── T001-<slug>/
│   │   ├── task.md
│   │   └── session-log.md
│   └── T002-<slug>/
│       ├── task.md
│       └── session-log.md
├── validation-and-integration.md
└── herdr-runbook.md
```

Create only artifacts needed by the initiative, but keep their canonical responsibilities. Herdr is the default runtime, so include `herdr-runbook.md` unless the user explicitly selects another runtime. The business plan remains usable without that file; it is a runtime adapter and may be removed or replaced.

Do not overwrite an existing initiative without inspecting it.

## Canonical artifacts

- bigplan.md: initiative name, destination, plan status, selected/default runtime (Herdr), branch strategy, links to canonical files, and completion gates. It is navigation, not a substitute summary.
- context-and-decisions.md: full relevant user context, observed behavior, examples, constraints, non-goals, decisions, assumptions, unresolved questions, source paths, repository configuration findings, affected-service style decisions, and third-party dependency findings. Distinguish facts, inferences, and user decisions.
- business-rules.md: complete initiative-wide rules outside task files. Give each rule a stable ID, full normative statement, known examples/edge cases, source evidence, and affected behavior. Do not paraphrase rules into shorter task-local versions.
- solution-design.md: selected solution and rationale, domain concepts, data/API/event contracts, state transitions, security behavior, failure handling, and compatibility requirements as applicable. Separate settled decisions from open options.
- work-map.yaml: static dependency graph, task metadata, dependencies, exact file sets, contracts, TODO handoffs, validation links, and integration outcomes. Follow references/work-graph.md.
- tasks/Txxx/task.md: full bounded task specification described below.
- tasks/Txxx/session-log.md: append-only execution and evidence history described in references/task-session-lifecycle.md.
- validation-and-integration.md: per-task, per-affected-service checks proving business outcomes and combined flow. Include applicable code, API, migration, configuration/startup, and third-party integration checks, exact commands/procedures, environments, expected results, and evidence locations. Mark non-applicable checks with a reason. Read references/dependency-and-verification.md.
- herdr-runbook.md: a disposable runtime-specific guide generated by reading current Herdr docs and installed CLI help. It includes verified commands and exact navigation/dispatch/status/wait/resume/reporting procedures for this plan. Read references/runtimes/herdr.md. Do not copy unverified commands from memory.

## Required task.md content

1. Task ID and observable business outcome.
2. Why the outcome is needed and how it supports the initiative destination.
3. Prerequisites and exact handoff artifacts/contracts, including any TODO that this task must resolve.
4. Complete applicable rule IDs and paths to canonical sources.
5. Exact repository-relative paths classified as read, create, or modify. Add symbol or line anchors only when verified.
6. Affected service/module and its recorded code-style references and decisions.
7. Applicable dependency/configuration checks and task verification checklist, linked to validation-and-integration.md.
8. Work sequence with meaningful substeps, decision points, and artifact produced at each substep.
9. Interface and behavior expected at task boundaries.
10. Acceptance conditions and evidence for each.
11. Known risks, edge cases, out-of-scope changes, and escalation conditions.
12. Integration notes, including shared-file ownership and merge/handoff requirements.

Do not say “implement per spec.” Do not invent exact classes, signatures, tests, commands, or payloads without repository evidence or a settled design. Do not require tests unrelated to the change.

## No lossy summaries or placeholders

Do not summarize away requirements, rules, decisions, interfaces, constraints, dependencies, acceptance conditions, or source paths needed to build or validate the work. A short index or dispatch may link to canonical files but must identify exactly which complete files/sections to read. Label genuine unresolved decisions and their impact. A plan is not ready if it has placeholders, undocumented assumptions, unresolved write ownership, or unobservable acceptance criteria.

## Branch and completion contract

Before implementation edits, create a new initiative branch from the current intended base. Record its exact name, base branch/commit, and initial working-tree state in bigplan/session logs. Never edit the primary branch as the initiative's working branch. Preserve uncommitted changes: do not reset, discard, or silently commit them; if branch isolation cannot preserve them safely, stop and report the exact blocker.

The initiative branch is the integration target. Task completion is not initiative completion. Every in-scope TODO handoff must be resolved, connected work must be integrated, and the final combined acceptance checks must pass before the initiative is marked complete. Do not merge to the primary branch unless the user asks.
